## 1. 已确认需求、适用范围与边界

### 1.1 需求依据

| 状态 | 内容 |
| --- | --- |
| 用户已确认 | 团队为 5–10 人；组长负责架构、方向、审核、最终合并和统一测试；组员负责不同功能及其测试 |
| 用户已确认 | 团队通过 VS Code 和 Codex 开发，缺少独立阅读和审查代码的经验，尽量减少手动命令行操作 |
| 用户已确认 | 取消 GitHub 自动验证，以本地验证为主；GitHub 用于仓库同步、PR 和合并，不配置 GitHub Actions |
| 沿用已讨论方案 | 使用 main、develop 和短期任务分支；组长可用独立审核 WorkTree；每人独立克隆仓库 |
| Codex 建议，本文作为默认规范 | 每项任务一个负责人、一个分支、一个 PR；组长串行合并；统一使用 Create a merge commit 合并方式；审核结果绑定具体提交 |
| 基于资料推断 | 当前仓库用于 Git/WorkTree 演示，现有资料未提供实际软件的技术栈和测试入口，不能据此确定应用测试命令 |
| 待项目启动时确认 | 实际技术栈、运行版本、启动与检查命令、数据库与测试数据、兼容范围、性能目标、发布环境及人员名单，见第 17 节 |

### 1.2 适用场景和目标

适用于成员各自实现功能、组长集中审核集成的小型软件项目。团队成员负责判断需求和操作结果，Codex 协助理解代码、实现、审查和执行测试。

交付一个任务的结果应包含功能代码、必要测试、相关文档和可复核的本地验证记录。每次验收只覆盖已执行的检查及其版本，不承诺软件不存在其他问题。

### 1.3 非目标和范围控制

- 本规范不配置 GitHub Actions、云端测试、云端 AI 审查或自动部署。
- 本规范不预设应用语言、框架、数据库或测试工具，也不把示例命令当作实际项目配置。
- 合并进入 main 与发布上线分开；发布需要组长针对具体版本另行确认。
- 任务只修改完成验收条件所需的内容。额外重构、新依赖、公共接口或数据库结构变化先由组长评估。
- 文件和目录通过 VS Code 资源管理器或编辑器创建；本文不提供创建文件的脚本。

## 2. 角色与责任

| 角色 | 负责事项 | 输出与决策权限 |
| --- | --- | --- |
| 组长 | 架构与接口、任务拆分、优先级、公共资源协调、独立审核、集成与发布验收 | 确认需求、批准跨模块变更、决定合并和发布，维护版本记录 |
| 任务负责人 | 在自己的任务分支实现功能、编写必要测试、执行自测、修复审核问题 | 提交任务 PR、验证记录和手动验收步骤；按约定不直接更新 main/develop |
| 开发 Codex 会话 | 阅读需求与规则、提出实现方式、编写代码、执行检查 | 给出实际变更与执行证据；如实列出失败和未验证项 |
| 审核 Codex 会话 | 对照需求检查差异、寻找遗漏和回归、复现问题、执行独立检查 | 给出有依据的问题和验证结果；最终合并由组长决定 |

组长开发自己的功能时，也走任务分支和本地验收流程。可请另一位成员进行实际操作验收，并使用新的 Codex 会话审查。

没有有效分支保护或规则限制时，拥有写权限的成员通常也能直接推送或合并到 main/develop。“仅组长合并”在这种情况下是团队约定，不是已生效的平台权限。需要技术限制时，由组长另行确认适用的仓库权限方案。

## 3. 仓库、分支与任务状态

### 3.1 基本结构

每位成员使用自己的 GitHub 账号、自己的本地克隆和登录凭据。一个克隆内部的 WorkTree 共用 Git 历史与分支信息，不在成员之间共享工作目录。

| 分支 | 用途 | 从哪里创建 | 合并到哪里 | 生命周期 |
| --- | --- | --- | --- | --- |
| main | 已通过整体验收的稳定版本 | 项目初始化 | 发布后将新增历史同步回 develop | 长期保留 |
| develop | 功能集成和统一测试 | 初始可运行的 main | main | 长期保留 |
| feature/T012-login | 一项功能任务 | 最新远端 develop | develop | 合并并确认记录后删除 |
| fix/T018-export | 一项普通缺陷修复 | 最新远端 develop | develop | 同上 |
| review/T012 | 组长本地合并候选与审核 | 本次锁定的 develop 提交 | 通常不推送、不作为 PR 来源 | 审核完成后清理 |
| hotfix/T020-login | 稳定版紧急修复，仅必要时使用 | 最新远端 main | main，随后同步到 develop | 验收完成后清理 |

分支名使用英文、数字和连字符；任务编号用于关联需求、提交、PR 和检查记录。按任务创建短期分支，不建立每人一个永久开发分支。

### 3.2 正常流转

1. 组长在可运行基线上确定任务及接口。
2. 组员从最新 develop 创建任务分支，开发并本地自测。
3. 组员推送任务分支并提交指向 develop 的 PR。
4. 组长本地审查、测试合并候选并实际操作验收。
5. 验收通过后合并到 develop，并检查实际合并结果。
6. 一批功能完成整体验收后，通过发布 PR 合入 main。
7. 同步 main 的新增历史回 develop，开始下一轮任务。

任务状态统一为：待澄清 → 待开发 → 开发中 → 自测中 → 待审核 → 审核中 → 已合并 → 版本已验收。审核发现问题返回“开发中”；有外部依赖无法继续时标记“阻塞”，写明负责人和解除条件。

### 3.3 合并方式

本文默认功能 PR、发布 PR 和分支同步 PR 都使用 GitHub 的 **Create a merge commit**。仓库管理员需确认该选项可用。这样长期分支的共同历史容易维护，也便于追踪任务。

如团队改用 squash 或 rebase，组长应先更新本规范中的候选版本验证、分支同步及撤销步骤。成员不临时切换合并方式。

## 4. 项目内应具备的资料

以下为实际项目应逐步具备的资料，可复用已有目录，不要求为小任务建立大量重复文件。除本规范外，表中路径均是建议结构，不表示已创建。

| 资料 | 建议位置 | 内容 |
| --- | --- | --- |
| 项目入口 | README.md | 用途、环境要求、启动、检查入口、文档导航 |
| Codex 项目规则 | AGENTS.md | 任务边界、需要阅读的规范、验证要求、提交和外部操作约定 |
| 架构及接口 | docs/architecture.md、docs/interfaces.md | 模块职责、依赖方向、接口输入输出、错误处理、数据约定 |
| 任务记录 | docs/tasks/ 或 GitHub Issue | 任务负责人、范围、依赖、验收条件和变更记录 |
| 本地检查指南 | docs/testing.md | 实际命令或 VS Code 任务、所需环境、测试账号与数据准备办法、结果位置 |
| 版本记录 | CHANGELOG.md 或 docs/releases/ | 版本内容、验收、未决限制、回退信息 |

测试输出和截图可保存在团队约定的本地记录目录中，并将脱敏摘要附到 PR。大量日志、依赖目录、构建产物及本地密钥不加入源码提交。

## 5. 组长的一次性准备

1. **建立仓库与成员访问。** 由组长维护私有仓库，邀请成员各自接受邀请。确认成员可拉取和推送自己的任务分支，说明 main/develop 的合并约定。
2. **准备可运行的骨架。** 完成基本目录、关键依赖和一条能运行的最小业务流程。架构先明确职责与接口，允许后续迭代，不等待所有模块完成才分工。
3. **建立开发基线。** 验证骨架后保留 main，从该基线建立 develop。现有项目若已有历史，由 Codex 先检查状态再协助准备，保留原有工作。
4. **统一环境。** 确定 Git、语言运行时、包管理器及数据库版本；记录 Windows 环境的启动方式。仓库保留依赖锁文件，本地配置使用示例文件说明变量用途。
5. **建立本地检查入口。** 让 Codex 根据项目实际配置整理检查方法；适合时配置 VS Code“运行任务”和测试面板，使成员能点击执行。只有实际配置后才称为“一键检查”。
6. **建立关键测试。** 至少覆盖最小业务流程和主要失败场景。单纯能启动或成功打包不足以替代功能验证。
7. **试走一个小任务。** 一名成员独立克隆、启动、开发、自测、提交 PR；组长完成本地审核和合并，再让另一名成员从更新后基线复现启动与检查。

完成条件：上述流程能走通，启动与检查入口有记录，团队知道遇到失败向谁反馈。具体工具尚未选择时，先完成文档规划，不声称本地检查已经建立。

## 6. 组员日常操作流程

### 6.1 领取任务并确认范围

阅读任务卡、架构、接口和项目规则。对无法判断的业务行为先向组长确认。示例：“实现登录”应细化为正确凭据的结果、错误凭据的提示、未登录访问的行为等可操作条件。

完成条件：任务有负责人、范围、依赖及逐项验收标准，相关公共接口已经确定。建议将任务拆到约 1–2 个工作日内可验收；超过时与组长拆分，实际工期以任务复杂度为准。

### 6.2 准备分支与目录

在 VS Code 确认当前文件夹和左下角分支。使用“源代码管理”查看未提交修改；需要保留的内容先提交到原任务分支，或明确使用 Stash（临时收起改动），记录恢复位置。暂存区的“暂存”仍属于未提交改动，不能当作独立备份。

本地干净后切到 develop，获取并拉取更新，再从最新 develop 创建任务分支。若拉取提示分叉或冲突，先让 Codex 解释状态并处理，不强推覆盖远端。

完成条件：正确仓库、正确任务分支、最新开发基线，且没有混入其他任务的修改。遇到 WorkTree 占用分支的提示时，在对应窗口处理或使用另一任务分支，不强制解除保护。

### 6.3 使用 Codex 实现

提供任务卡并要求 Codex 先读相关规则、既有实现和接口。先说明计划修改的模块，再实施任务。保持现有页面风格、模块边界和依赖约定。

修改公共组件、数据库结构或接口时，先说明影响，由组长协调相关负责人。独立任务可以同时推进；有前置依赖的任务等基础改动合入 develop 后再开始，避免成员私下交叉合并难以追踪。

完成条件：代码与必要测试已经形成，改动范围可解释；需求变化已经同步到任务卡。

### 6.4 本地自测和实际操作

让 Codex 按第 8 节选择并实际执行检查；组员按验收条件亲自操作软件，覆盖正常情况和主要异常情况。检查问题时区分代码失败、环境问题和需求未明确。

完成条件：必要检查通过，每项验收条件有对应证据；未执行项标记原因与影响，不填写“通过”。没有测试框架时，先记录手动验证，再与组长建立必要自动测试。

### 6.5 提交与推送

在源代码管理面板逐个查看变更，确认只含任务相关文件；选择需要的文件暂存，写清楚提交说明，例如“T012：增加登录失败提示”，再提交到任务分支。

提交后，确保已测代码都包含在提交里，工作区没有影响运行结果的遗漏修改；记录任务提交 SHA，再推送。首次使用“发布分支”，以后使用“推送”。“同步更改”通常同时涉及拉取与推送，状态不清楚时分别操作。

完成条件：预期提交已推送到正确远端的任务分支，PR 能引用该版本。新文件需要加入版本控制；只用“提交已跟踪修改”可能遗漏新文件。

### 6.6 提交 PR 和修复审核问题

通过 GitHub 网页或 VS Code 的 GitHub Pull Requests 扩展创建 PR。普通任务的目标（base）为 develop，来源（compare/head）为自己的任务分支。按第 14 节填写交付材料。

需要补充内容时继续在原分支提交并推送，同一个 PR 会更新；补充内容必须重新验证。组长只合并已完成的任务，尚未就绪的 PR 标记为草稿或明确写“暂不合并”。

完成条件：组长能按材料复现功能；审核问题逐项关闭，最新版本的检查记录已更新。

### 6.7 合并后开始新任务

确认 PR 已合并，再更新本地 develop。保留必要的交付和检查记录，确认没有独有提交或未保存内容后清理旧任务分支；关联 WorkTree 的清理见第 9 节。下一任务从最新 develop 新建分支。

## 7. 组长本地审核与功能合并

### 7.1 接收与初筛

确认任务范围、负责人、PR 来源和目标。检查是否包含不相关文件、意外删除、密钥或本地数据；核对自测记录和手动验收步骤。材料不足时退回补充。

GitHub Checks 没有结果，在本流程中不等于检查通过，也不表示流程故障；合并依据来自本地验证记录。

### 7.2 准备可复核的候选版本

1. 获取最新远端信息，锁定目标 develop 的提交 B 和任务分支提交 F，记录完整 SHA。SHA 是 Git 提交的唯一标识，可让 Codex 读取。
2. 在独立审核 WorkTree 中，从 B 创建临时 review 分支，并把 F 合入，形成候选提交 C。候选合并使用与 PR 一致的保留历史方式。
3. 工作区保持干净，记录 C 及其文件树标识。文件树标识代表 Git 跟踪文件的完整内容，可由 Codex 比较，无需组长手动记忆命令。
4. 有冲突时先停止验收。让任务负责人在功能分支中合入最新 develop，结合需求解决冲突、测试并推送，再从新的 B/F 开始准备候选。审核目录中的临时修复不能代替任务分支的正式修改。

完成条件：候选版本可从记录的 B/F 复现，没有未解决冲突，也没有未提交的修补内容。

### 7.3 独立 AI 审核与人员验收

使用新的 Codex 会话阅读任务、相关架构与差异，检查实现是否符合需求、是否影响已有接口、权限、异常和数据处理。审核会话默认只提出问题与证据，问题交回负责人修复。

在候选版本上执行第 8 节的适用检查。组长再按验收清单操作功能，并检查与其他模块联动的场景。新会话能减少沿用开发时假设的倾向，但不能保证模型一定找出所有缺陷。

完成条件：必要检查通过，需求逐项验收通过，阻塞问题已关闭；非阻塞问题有影响说明、负责人和处理时间。

### 7.4 合并前最后核对

组长逐个处理待合并 PR。点击合并前重新获取远端，确认 B 和 F 均未变化；任何一方变化，都要基于新的 B/F 重建候选、审查新增差异，并重新完成该 PR 要求的验收和必要检查。只有能说明某项既有检查不受变化影响、且对应源码 SHA 未变时，才可复用该项记录，并在审核记录中写明依据。不能用旧 B/F 的整体结果批准新版本。

确认 PR 仍指向 develop，并使用约定的 Create a merge commit。GitHub 若提示冲突、分支更新或其他异常，返回处理；不用网页临时修代码后立即合并。

### 7.5 合并后的实际版本检查

拉取实际远端 develop，记录合并后的提交 M。让 Codex 比较 M 与已测候选 C 的文件树内容。GitHub 生成的提交 SHA 与本地 C 不同是正常的，不能仅因 SHA 不同判定代码不同。

文件内容一致时，仍对实际版本执行启动和关键业务冒烟检查；有构建依赖提交信息等特殊情况时验证实际产物。内容不一致时查明差异，对实际版本重新检查，问题解决前暂停后续合并。

完成条件：实际合并版本有记录，内容核对与关键检查通过。然后将任务标记为已合并；“版本已验收”由第 10 节完成。

## 8. 本地验证标准与证据

### 8.1 按改动选择检查

| 检查 | 解决的问题 | 使用方式与证据 |
| --- | --- | --- |
| 变更范围检查 | 是否误改、漏提文件或混入其他任务 | 查看差异、文件列表和任务范围 |
| 静态检查 | 语法、类型、规范等可自动发现的问题 | 执行项目已配置的检查，保存命令、退出码和输出摘要 |
| 自动测试 | 业务规则、接口、异常和历史功能是否符合预期 | 执行相关测试及必要回归，记录通过、失败、跳过数量 |
| 构建检查 | 项目能否完成编译或打包 | 执行实际构建并检查退出结果；构建成功不等于功能正确 |
| 启动与冒烟检查 | 软件是否能启动、关键路径是否可用 | 记录服务、页面及主要流程的实际结果 |
| 功能与异常验收 | 用户场景是否达到任务要求 | 逐项记录输入、预期、实际结果，必要时提供截图 |
| 集成与兼容检查 | 多模块、目标浏览器或目标系统一起工作是否正常 | 在候选和实际集成版本验证受影响流程与目标环境 |
| 数据与性能检查 | 数据迁移、重复提交、量级或响应时间是否满足本任务要求 | 涉及时使用隔离测试数据并按已确认指标测量 |

文档修改可只检查内容、链接和预览；界面改动需检查主要状态、约定视口和现有风格；业务代码需验证行为；接口或数据库改动需验证调用方与数据影响。根据风险选择检查，不用与改动无关的全套测试替代关键场景。

项目测试命令由实际配置确定并写入检查指南。本规范不假设一定存在某个 npm、Python 或其他工具命令。缺少必要测试时由负责人补充；临时采用手动检查需要记录理由和可信范围。

### 8.2 记录规则

- 每轮记录包含任务/PR、执行人、日期、操作系统与关键运行版本、源码 SHA、目标分支 SHA、实际命令或 VS Code 任务名、结果及日志位置。
- 组长记录额外包含候选 C、实际合并 M 和内容比较结果。关键证据要能在本地重新复现。
- 执行结果分为“通过、失败、未执行、不适用”。跳过测试不能计入通过；不适用需写明原因。
- 测试时如果存在会影响结果的未提交修改，应先整理为可复现的提交并重测。测试后再改代码，原记录不能证明修改后的代码通过。
- 环境失败保留错误和复现信息。无法执行的必要检查视为未验证，先修复环境或由组长安排替代验证后再决定。
- 问题修复后运行受影响检查和必要回归。通过减少断言、删除有效测试或隐藏错误来换取通过不符合本规范；测试本身有错时说明依据并审查修正。

### 8.3 问题分级和合并条件

| 等级 | 示例 | 处理 |
| --- | --- | --- |
| 阻塞 | 核心验收失败、启动或必要测试失败、越权、数据损坏、接口不兼容 | 修复并复测后才能合并 |
| 一般 | 有明确影响但不影响本次关键验收的缺陷 | 组长判断是否仍需阻塞；允许后续处理时记录理由、负责人和期限 |
| 建议 | 非必要的优化、文案或结构改进 | 可拆新任务，避免顺手扩展当前范围 |

合并门槛：任务范围清楚、必要本地检查通过、实际操作通过、阻塞问题关闭、记录对应当前版本、组长明确批准。AI 的“未发现问题”不单独构成批准依据。

## 9. WorkTree 与本地运行隔离

普通组员初期使用一个克隆、一个当前任务即可；需要并行处理独立任务时再使用 WorkTree。组长建议保留日常开发目录，并按审核任务创建独立 review WorkTree。

创建目录或 WorkTree 可交给 Codex；若当前 VS Code 版本提供相应 Git 功能，也可使用其菜单。每个目录用单独窗口打开，确认 Codex 会话、终端和 Git 仓库选择都指向该目录。一个分支通常只能在同一克隆的一个 WorkTree 中检出。

WorkTree 只隔离文件和索引，不自动隔离依赖、端口、环境变量、数据库或外部服务。并行启动时分配不同端口；涉及数据库或迁移时使用隔离的测试库/数据；需要本地环境文件时按项目示例配置并保持在 Git 忽略范围。也可以串行启动，避免无谓维护多套服务。

清理前停止该目录的服务，保存审核记录，确认没有未提交内容和未保留的独有提交。由 Codex 通过 Git 正常移除 WorkTree，再清理不再需要的临时分支；不直接删除文件夹后假定 Git 登记已同步，也不默认强制删除。

## 10. 整体验收、稳定版本与发布

1. **确定版本范围。** 组长列出本批任务和未决问题。进入验收窗口后暂停向 develop 合入无关新功能，成员可以继续在自己的分支开发。
2. **测试集成版本。** 从干净工作区按文档启动最新 develop，执行完整版本验收所需的本地测试、构建和跨模块业务流程。至少让另一台成员电脑按文档复现关键启动与操作，排查个人环境依赖。
3. **准备发布 PR。** 创建 develop 指向 main 的 PR，记录版本号、任务列表、验证记录、已知限制及回退办法。对最新 main 与 develop 的合并候选按第 7 节同样核对和验证；main 若已有紧急修复，不能忽略其影响。
4. **合并并确认实际版本。** 组长批准后按统一方式合并，拉取实际 main，核对内容并做关键回归。失败时暂停发布并按第 11 节处理。
5. **记录稳定版本。** 在确认后的 main 提交上创建版本标签并保存版本记录。标签如 v0.1.0；已经发布的标签不移动，修正时使用新版本。推送标签、部署或更新线上数据均应取得针对该次操作的明确授权。
6. **同步开发基线。** 将 main 的新增历史通过 PR 合回 develop，包括发布合并提交、版本信息或紧急修复。必要时解决冲突并本地验证；文件内容未变也可用于统一历史。后续任务从同步后的 develop 开始。

版本验收结束条件：发布范围逐项通过、实际 main 内容已确认、已知限制已记录、版本标签可追溯、main 的新增历史已同步到 develop。是否上线以及上线是否成功单独记录。

## 11. 异常处理与回退

| 情况 | 正确处理 |
| --- | --- |
| 本地有未提交修改，需要换分支 | 先保留到原任务提交或明确使用 Stash，记录位置；确认工作状态后再切换 |
| 远端有更新或推送被拒绝 | 获取最新信息，确认分叉原因，在任务分支正常合并处理并重测；不强推覆盖别人工作 |
| 合并冲突 | 负责人结合双方需求逐处处理，必要时请组长协调；不盲目全部接受“当前”或“传入”；解决结果必须进入提交并重测 |
| 审核期间任一分支更新 | 更新候选，审核新增差异并重测；旧验证记录保留为历史，不作为新版本合并依据 |
| 自动测试无法运行 | 记录环境和错误，修复或安排替代本地验证；必要检查未验证时暂停合并 |
| 意外提交到 main/develop | 立即停止推送并通知组长，先保留提交，再由 Codex 检查是否已共享，制定不丢失工作的恢复步骤 |
| develop 合并后出现问题 | 暂停后续合并，评估小修复或通过撤销 PR 回退，并测试实际恢复结果 |
| 稳定版紧急问题 | 从 main 创建 hotfix，优先验证缺陷和关键回归；合入 main 后，将修复及历史同步回 develop |
| 需要撤销已共享提交 | 优先使用 revert 生成反向提交并走 PR；由 Codex 确认普通提交还是合并提交、后续依赖和撤销范围 |
| 需要恢复到历史版本 | 先明确“撤销某项修改”还是“恢复整个文件状态”；旧提交上新建分支只是另开开发线，并不会改变当前 main |

撤销某个提交只反向处理该提交的改动，不保证仓库等同于某个历史版本。合并提交的撤销还涉及主线父提交的选择。共享 main/develop 不使用 reset 加强制推送改写历史；数据迁移的回退也不能仅靠代码 revert 完成。

撤销过的功能以后需要重新引入时，由组长制定修复或重新引入方案；不能假定再次合并原分支就会恢复该功能。

## 12. VS Code 操作对照与少量只读命令

菜单名称会随版本、语言和扩展变化。找不到入口时使用命令面板搜索 Git 操作，或明确让 Codex 执行；本文不假设某个 WorkTree 菜单在所有版本都存在。

| 目的 | 推荐操作 |
| --- | --- |
| 首次获取项目 | 命令面板搜索 Git: Clone，输入仓库地址并打开文件夹 |
| 确认当前分支 | 查看左下角分支名；多仓库窗口同时确认源代码管理中选中的仓库 |
| 获取远端状态 | 源代码管理的 Git 菜单中选择 Fetch/获取 |
| 更新当前分支文件 | 状态明确后选择 Pull/拉取；它会整合当前分支关联的远端更新 |
| 创建/切换任务分支 | 点击分支名，或在命令面板搜索创建分支、签出；先确认基线和未提交内容 |
| 新建任务文件 | 使用资源管理器“新建文件夹/新建文件”，输入名称并在编辑器填写内容 |
| 检查并提交 | 点击变更文件查看差异，选择需要的文件暂存，填写说明并提交 |
| 推送任务分支 | 首次“发布分支”，后续“推送”；确认远端地址和分支 |
| 运行检查 | 已配置时使用测试面板或“终端 → 运行任务”；否则让 Codex 按项目指南执行并展示结果 |
| 创建/查看 PR | 使用 GitHub Pull Requests 扩展或 GitHub 网页，核对来源和目标 |
| 审核另一个任务 | 用独立审核 WorkTree，在新 VS Code 窗口打开；交给 Codex 准备候选版本 |

Fetch 更新远端分支信息，Pull 会获取并整合到当前分支，Push 上传本地提交，PR 请求把一个分支合入另一个分支。它们不能相互替代。

以下只读检查可让 Codex 执行；每行末尾均说明作用。比较前先获取最新远端信息，diff 示例在任务分支运行。

```powershell
git status --short --branch                 # 查看当前分支与未提交文件状态
git branch --show-current                   # 显示当前分支名称
git log -5 --oneline                         # 查看最近五次提交及短编号
git rev-parse HEAD                          # 记录当前提交的完整 SHA
git diff origin/develop...HEAD --stat        # 查看任务分支相对 develop 共同祖先的变更规模
git diff --check origin/develop...HEAD       # 检查分支差异中的空白等问题，不代表功能测试通过
git worktree list                           # 查看当前克隆登记的 WorkTree 和分支
```

## 13. 共享接口、数据、风格与安全约定

- 模块间通过已确认接口协作，记录输入、输出、错误和兼容约定。公共改动由组长协调，必要时先合入基础任务。
- UI 先复用项目页面、组件、样式令牌、图标和文案习惯。验收时检查主要状态及约定视口，新增风格要明确说明。
- 兼容范围由任务卡和项目检查指南确定，包括实际支持的系统、浏览器和运行时版本；不能只凭一台电脑成功宣称全部兼容。
- 性能要求涉及响应时间、数据量或并发时，先明确测量环境和目标，再记录实际结果。没有测试的数据不能写成性能结论。
- 密钥、令牌、密码、真实业务数据及本地环境文件不进入源码、PR 和公开日志。测试账号使用专用测试权限与脱敏数据。
- 数据库结构调整要记录升级步骤、测试数据影响及恢复办法。迁移先在隔离环境测试，线上操作由组长另外确认。
- 依赖升级、锁文件修改和环境变化需有任务依据，并验证相关运行行为；本地检查本身不额外要求调用付费模型或云端服务。

## 15. 可交给 Codex 的自然语言指令

以下模板由当前操作人补全任务或 PR 标识。推送、合并、部署、删除资料等操作要依据当前会话的明确授权；已有授权时按授权范围继续，不重复询问。

### 15.1 组员开始任务

> 我负责【任务编号】，任务要求和验收条件见【路径或内容】。请先阅读项目 README、AGENTS.md、开发规范及相关架构接口，确认当前目录、分支和未提交修改。保留已有工作，从最新 develop 准备短期任务分支。先说明范围与实现步骤，再完成开发和适用的本地测试。公共接口或需求不明确时指出影响并向我确认。报告实际修改、检查结果、未验证项和我可以照做的验收步骤。此次范围是本地开发与验证；推送或创建 PR 按本会话授权执行。

### 15.2 组员提交前检查

> 请对照【任务】检查当前任务分支相对最新 develop 的改动，核对误改、漏提文件、接口影响和验收条件。根据项目实际配置运行必要检查，并给出执行命令、退出结果和日志位置。保留测试失败信息，解释失败原因。整理可复现提交并确认工作区状态，记录验证版本，生成 PR 说明草稿。未执行项标为未验证，等待我完成实际操作验收。

### 15.3 组长审核 PR

> 请审核【PR/来源分支】，任务要求是【路径或内容】。获取最新远端，记录目标 develop 和来源分支的完整 SHA，在独立审核 WorkTree 中准备临时合并候选，保留我的其他工作。对照需求和接口审查差异，运行适用本地测试、构建与集成检查；报告问题依据、复现步骤和未验证项，再给我手动验收清单。问题修复应回到负责人分支。请准备审核记录并等待我的合并决定，不把审核结论当作合并授权。

### 15.4 组长确认合并及实际结果

> 我已完成【PR】的验收，授权合并这一项。请先核对远端目标与来源提交仍等于已测记录，确认 PR 目标和合并方式正确。如果版本已变，先重新准备候选并验证，向我报告变化后再决定。版本一致时执行已授权合并，再获取实际目标分支，比较它与候选的文件内容，运行必要冒烟检查并更新记录。若无法执行 GitHub 操作，请说明原因并给出我可在网页完成的步骤。

### 15.5 集成失败或需要撤销

> 【版本/PR】出现【现象】。请先保存当前工作并检查 Git 历史、复现条件和本地日志，判断是该改动、其他提交还是环境导致。比较修复与 revert 的影响，说明是否涉及合并提交、数据变化及后续依赖，给出可复核方案。先完成获授权的本地诊断与验证；对共享分支的推送、撤销合并和数据恢复按我的明确授权执行。

## 16. 启用与交付检查单

启用流程前由组长确认：

- [ ] 每位成员有独立账号和克隆，知道正确仓库地址及角色约定。
- [ ] main、develop 已建立，合并方式和最终负责人已明确。
- [ ] 新成员能按文档启动项目并运行规定的本地检查。
- [ ] 架构接口、任务卡、验证记录和 PR 说明有可用入口。
- [ ] 组长能够在独立目录准备候选并复现功能。
- [ ] WorkTree 涉及的服务端口、配置和测试数据不会相互干扰。
- [ ] 一个小任务已完整走过成员自测、组长审核、合并后复核。
- [ ] 已明确本流程不依赖 GitHub 自动检查，也未把缺失的检查结果当作通过。

任务交付和版本交付分别以第 8.3 节、第 10 节的完成条件为准。以上检查单为空表示尚待实际项目启用时执行，不表示本次文档制作已经完成了这些配置。

## 17. 待确认事项与变更管理

| 待确认事项 | 负责确认者 | 截止条件 |
| --- | --- | --- |

| 发布环境、操作人及数据恢复办法 | 组长 | 第一次发布前 |

需求变更时同步修改任务范围、假设、接口、验收条件和验证计划。规范变更时更新版本号和本节记录，并通知正在进行的任务按受影响内容调整。

本仓库的 [README](../README.md) 是简化 WorkTree 演示；其中直接合入 main 的练习不作为本规范的日常协作流程。此前 GitHub Actions 调研为历史资料，不构成当前检查要求。
