# 小组开发流程简版：组员与组长

版本：v1.0
适用团队：5–10 人，使用 VS Code + Codex，GitHub 只做代码同步和 PR，检查以本地为主，不配置 GitHub Actions。

## 共同约定

- `main`：已经通过整体验收、可以作为稳定版本的分支。
- `develop`：组长集成功能和统一测试的分支。
- `feature/T编号-功能名`：一项任务一个短期分支，完成并合并后删除。
- 每个人使用自己的 GitHub 账号和自己的克隆目录，不共用同一个工作目录。
- 一个 WorkTree 只能检出一个分支。VS Code 每个 WorkTree 单独打开一个窗口，并先确认左下角分支名、窗口路径和源代码管理中的仓库。
- 组员提交 PR 到 `develop`；组长审核并合并。没有分支保护时，“只有组长合并”属于团队约定。
- 本地测试、构建和手动验收由 Codex 协助执行，但组员和组长必须查看实际结果；没有执行的项目写“未验证”。

## 组员操作

### 1. 接收任务

从任务卡或组长消息确认任务编号、目标、验收条件、负责目录、接口约定和依赖任务。先在 VS Code 打开自己的项目克隆，阅读项目 `README`、`AGENTS.md`、架构说明和本任务资料。

在 Codex 中说明：任务编号、验收条件、当前目录、当前分支，以及“请先阅读相关规则并说明计划，保留已有修改，不要直接操作 `main` 或 `develop`”。

### 2. 更新基线并创建任务分支

确认没有未保存或未提交的工作后，在 VS Code 的源代码管理或命令面板中获取远端更新，并切换到 `develop` 后拉取最新内容。再从最新 `develop` 创建任务分支，例如 `feature/T012-login`。

如果一个人需要同时处理互不相关的任务，在自己的克隆中为每项任务建立不同 WorkTree；不要让两个任务共用同一个目录或同一个分支。成员不需要使用组长的审核 WorkTree。

可让 Codex 只读确认状态：

```powershell
git status --short --branch       # 查看当前目录、分支和未提交文件
git branch --show-current         # 确认当前分支名称
git worktree list                 # 查看当前克隆的 WorkTree 和分支
```

### 3. 使用 Codex 开发

把任务卡和验收条件交给 Codex，要求它先检查现有实现、接口和项目风格，再说明计划。开发过程中只修改任务范围内的文件。

修改公共接口、数据库结构、共享组件、依赖或配置时，先暂停并向组长说明影响。需求不清楚时先确认，不用猜测结果扩展范围。

### 4. 本地检查和手动验收

让 Codex 根据项目实际配置执行适用的静态检查、自动测试、构建、启动和关键业务流程。然后由组员自己按验收条件操作一次，检查正常情况和主要异常情况。

要求 Codex 报告：执行的命令或 VS Code 任务、退出结果、测试摘要、日志位置、运行环境、未执行项目及原因。失败结果必须保留并解释，不能把“没有运行”写成“通过”。

### 5. 提交和推送

在 VS Code 的源代码管理面板逐项查看变更，只暂存本任务文件。提交前再次确认窗口路径、分支名、文件列表和远端仓库。

```powershell
git add <任务文件>                         # 将本任务文件加入暂存区
git commit -m "T012: 完成登录功能"          # 保存本次任务修改
git push -u origin feature/T012-login       # 首次推送任务分支并建立远端关联
```

记录本次提交的完整 SHA、测试命令、结果和未验证项。新文件必须确认已被加入提交；只提交已跟踪文件可能遗漏新文件。

### 6. 创建和维护 PR

在 GitHub 或 VS Code 的 Pull Requests 扩展中创建 PR：来源是自己的 `feature/...` 分支，目标是 `develop`。PR 说明写清任务、改动、验证命令和结果、手动验收步骤、已知问题及回退考虑。

组长退回问题时，回到原任务分支修改、重新检查、提交并推送。同一个 PR 会自动更新。每次新增提交都要重新执行受影响检查，并更新验证记录。

### 7. 合并后收尾

确认 PR 已由组长合并后，在 VS Code 更新本地 `develop`。确认任务分支没有未推送的独有提交，再删除已完成的任务分支和对应 WorkTree。下一项任务从最新 `develop` 重新创建分支。

## 组长操作

### 1. 建立和维护基线

维护 `main` 和 `develop`。`main` 只接收通过整体验收的版本；日常功能先进入 `develop`。为项目写清真实的启动、测试、构建入口和任务验收条件，并先用一个小任务试走完整流程。

组长开发自己的功能时，也创建任务分支并提交到 `develop`，由另一位成员或新的 Codex 会话协助验收，避免自己只检查自己的假设。

### 2. 接收 PR 初筛

确认 PR 的任务编号、负责人、来源分支和目标是否正确，检查是否混入无关文件、意外删除、本地配置、密钥或真实数据。检查组员是否提供提交 SHA、实际验证记录、手动验收步骤和未验证项；材料不完整就退回补充。

### 3. 建立独立审核 WorkTree

获取最新远端信息，记录目标 `develop` 的完整 SHA（B）和任务分支的完整 SHA（F）。在组长自己的克隆中建立临时审核 WorkTree，从 B 准备合并候选并合入 F。审核目录只用于验证，不在其中直接修复功能。

如果发生冲突，停止审核，要求负责人在任务分支合入最新 `develop`、解决冲突、测试并推送；然后从新的 B/F 重新准备候选。不要把网页临时解决冲突当成已经验证。

### 4. 使用 Codex 审核和本地验收

在独立审核 WorkTree 中开启新的 Codex 会话，提供任务要求、接口资料、B/F SHA 和候选版本。要求 Codex 检查需求覆盖、误改和漏改、接口影响、权限、异常、数据、兼容性和回归风险，并给出问题依据与复现步骤。

在同一个候选版本执行必要的静态检查、自动测试、构建、启动、集成测试和手动验收。组长亲自操作关键流程。审核结论只代表检查结果，不等于合并授权。

### 5. 合并前确认版本

点击合并前重新获取远端，确认 B 和 F 没有变化，PR 仍以 `develop` 为目标，并使用团队约定的合并方式。任何 B/F 变化都必须重建候选、审查新增差异，并重新完成该 PR 要求的验收和必要检查；只有能证明源码 SHA 未变且不受影响的单项检查才可复用，并写明理由。

### 6. 合并后检查实际结果

合并后拉取实际 `develop`，记录合并后的提交 M。让 Codex 比较实际版本和已测候选的文件内容，再对实际版本执行启动和关键业务冒烟检查。内容不一致或检查失败时暂停后续合并，查清原因并重新验证。

一批功能完成整体验收后，组长创建从 `develop` 到 `main` 的发布 PR。合并并验证 `main` 后，再把 `main` 合回 `develop`，确保发布提交、版本信息和紧急修复进入后续开发基线。

### 7. 处理异常和清理

- 推送被拒绝：先获取远端更新，判断分叉原因，在任务分支合并并重测，不强制推送覆盖他人提交。
- 合并冲突：由负责人结合双方需求解决，解决提交必须重新测试。
- 集成后发现问题：暂停后续合并，判断修复或 `revert`，并对实际恢复结果做验证。
- 审核完成：清理临时审核 WorkTree；任务分支在确认没有未合并提交后删除。

组长应保留任务 PR、B/F/C/M 提交记录、验证命令和结果、手动验收结论以及已知限制。GitHub 没有自动检查结果时，以本地记录和实际验收为依据，不能把缺失的检查当作通过。
